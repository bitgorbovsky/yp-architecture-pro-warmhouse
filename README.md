# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Система поддерживает включение и выключение регуляторов отопления,
  установленных в домах.
- Пользователи могут удалённо включать и выключать отопление в своих домах
  через мобильное приложение и web-интерфейс.

**Мониторинг температуры:**

- Система получает данные о температуре с датчиков, установленных в домах.
- Пользователи могут просматривать текущую температуру в своих домах через
  мобильное приложение и web-интерфейс.

**Регистрация датчиков**

- Техники компании могут регистрировать датчики и регуляторы отопления в
  системе.
- Техники компании могут удалять датчики и регуляторы отопления из системы.
- Техники компании могут просматривать записи обо всех заведённых в системе
  датчиках и регуляторах.

### 2. Анализ архитектуры монолитного приложения

* **Язык программирования**: Go
* **База данных**: PostgreSQL
* **Архитектура**: Монолитная, все компоненты системы (обработка запросов,
  бизнес-логика, работа с данными) находятся в рамках одного приложения.
* **Взаимодействие**: Синхроннное, запросы обрабатываются последовательно.
  Основной протокол взаимодействия: HTTP.
* **Масштабируемость**: Ограничена (монолитное приложение сложно масштабировать по частям).
* **Развёртывание**: Для текущего монолита развёртывание можно сделать и
  перекрывающим (старые запросы обрабатываются старой версией монолита, новые
  направлять уже на новую версию), но в случае тяжёлого монолита,
  требовательного к памяти и процессорным ресурсам, это развёртывание дорогое и
  может потребоваться развёртывание с полной остановкой всего приложения.


### 3. Определение доменов и границы контекстов

#### Устройства

- **Регистрация устройств** - заведение устройств в систему, их удаление.
- **Управление устройствами** - управление устройствами (изменение их
  состояния).
- **Телеметрия** - процессы обработки, хранения и отображения телеметрических
  данных с устройств.

### 4. Проблемы монолитного решения

- Отсутствуют средства безопасности (регистрация пользователей, авторизация,
  аутентификация). Все запросы могут выполнены кем угодно и с какими угодно
  данными в полях json-структур.
- Отсутствует привязка приборов к пользователям.
- Проблемы метода API `GET /api/v1/sensors`:
  - При большом размере таблицы `sensors` в БД может привести к сильной
    нагрузке на сервер, когда при большом количестве датчиков в системе будет
    запрошен полный список. Данная функциональность плохо масштабируется.
    Отсутствует постраничное API.
  - В случае пустой базы данных возвращает `null`, а не `[]`, что также
    рассматривать как нарушение принципов REST.
  - Нет защиты от перегруза датчиков. При большом количестве запросов (а также
    запросов вида `GET /api/v1/sensors/:id`), приложение запрашивает показания
    датчиков, что может привести к перегрузке сервера и самих датчиков.
    Перегруз системы приводит к потере управления, увеличению трафика, что
    может быть критично для пользователей с мобильными каналами связи.
  - Время выполнения запроса сильно зависит от времени выполнения запросов на
    получение показаний температурных датчиков, что в целом сильно влияет на
    конечную отзывчивость системы.
  - Отсутствует кеширование показаний датчиков (нет смысла выдавать каждый раз
    новое значение температуры, если оно меняется в целом довольно медленно, в
    пределах секунды показание датчика может и не измениться).
  - Запрос списка датчиков может выдавать данные, которые могут быть
    использованы разным способом: где требуется показать актуальное значение
    температуры, а где-то нет, но при обработке запроса вне зависимости от
    этого, происходит опрос датчиков. Нет возможности указать системе, в каком
    случае надо обновлять показания датчиков, а в каком случае нет.
- Проблемы метода API `DELETE /api/v1/sensors/:id`:
  - В случае отсутствия датчика возвращает статус 500 вместо ошибки 404, что
    можно рассматривать как нарушение принципов REST. Как следствие, это
    усложняет организацию мониторинга, когда отслеживается, сколько запросов к
    системе завершилось со статусом 50x - увеличивает количество ложных
    срабатываний.
- Проблемы метода API `PUT /api/v1/sensors:id`:
  - Управление прибором не отделено от изменения его состояния: можно поменять
    температурного датчика; назначить произвольный статус и так далее.
- Проблемы администрирования и развёртывания:
  - Нет возможности конфигурировать размер пула соединений к БД (для PostgreSQL
    это критично).

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081
